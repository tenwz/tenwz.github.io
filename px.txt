px: 让任何运行 Pi 的机器成为 Agent 服务

2026-09-13


Agent 最缺的可能不是更多工具，而是一个能保存上下文、等待现实世界变化，并在合适的时候继续工作的地方。


1. 为什么是 PX

现在做一个 Agent 并不难。让模型调用工具、读取文件、返回结果，已经有了成熟的运行时。真正难的是：当工作没有在一次请求里结束时，谁来记住它，谁来在未来把它重新叫醒？

Pi 已经是一个很好的 Agent runtime。它知道怎样组织上下文、调用工具、执行扩展，也知道怎样完成一次完整的 Agent Turn。PX 不应该再做一套 Agent runtime，更不应该把 Pi 已经拥有的能力重新包装一遍。

PX 想解决的是另一段缺失的生命周期：让运行在本机的 Pi 能够被应用访问，能够在进程停止后保留工作状态，并且在外部事件发生时继续工作。

    Pi 负责 Agent 能做什么。PX 负责它什么时候再次醒来。


2. 先把边界说清楚

PX 的核心不是把所有能力都收进来，而是把职责压缩到足够小：

    Pi
    ├── Session
    ├── Agent Runtime
    ├── Tools
    └── Extensions

    PX
    ├── Serve
    ├── Session lifecycle
    ├── Watch
    └── Recovery

外部服务的能力应该拆成两个运行位置：

- Pi Extension：Agent 主动做什么，例如搜索 Gmail、读取 Issue、发送 Slack。
- PX Event Source：未来发生什么，例如收到邮件、Issue 更新、Webhook 到达。

一个 Integration 可以同时提供这两部分，但它们不共享一个庞大的 Connector Runtime。共享的只应是凭证引用、配置和元数据。


3. Serve：让应用找到本地 Agent

Serve 是 PX 的入口。它提供一组与 OpenAI Agents API 核心语义兼容的接口，让已有的客户端可以用熟悉的方式创建任务、继续 Session、接收流式事件和读取结果。

    应用
      ↓
    Agents API 兼容层
      ↓
    PX Serve
      ↓
    Pi Session
      ↓
    本机环境

但 API 兼容本身不是产品价值。它只是降低接入成本的入口。真正有价值的是：请求断开以后，工作仍然存在；Pi 进程退出以后，Session 仍然可以恢复。


4. Session：工作的基本单位

一次请求通常太短。一项真实工作可能经历调查、修改、等待 Review，再回来处理新的反馈。PX 因此把 Session 而不是 Request 作为持续工作的基本单位。

    请求 A → Session → 调查 → 暂停
                              ↓
    请求 B → 同一个 Session → 修改 → 继续

Session 至少需要保证：

- 上下文和执行记录可以持久化；
- 客户端断线不会让工作消失；
- 同一 Session 不会同时执行两个互相竞争的 Turn；
- 进程崩溃后能够恢复到一个可解释的状态。


5. Watch：让未来的世界叫醒它

Agent 工作到一半时，经常只能等待：等待一封邮件、一个 CI 结果、一次 Review、一个时间点。如果 Agent 必须一直运行来等待，成本高，也很容易因为进程退出而丢失上下文。

Watch 把“等待”变成一种持久化声明：

    Session
       ↓ 留下 Watch
    PX Event Source
       ↓ 监听
    事件命中
       ↓
    恢复同一个 Session

Watch 不应该被设计成一套复杂的规则语言。用户可以用自然语言表达意图，Agent 决定需要监听什么；PX 只负责可靠地接收事件、去重、匹配，并在合适的时候恢复 Session。

能用代码判断的，不唤醒模型，例如特定发件人、CI 失败、定时器到点。需要语义理解的，再使用一个轻量判断步骤，例如“这是不是一封重要的邮件”。


6. 并发：不是让同一个 Agent 同时跑两条路

Pi 可以并发运行多个 Session，也可以在一个 Turn 内并行调用互不冲突的 Tool。PX 要做的不是重新发明并发，而是建立并发边界：Serve 可以高并发接收请求，但同一 Session 仍然应该只有一个执行通道。

- 不同 Session、不同项目、互不冲突的只读任务，可以并发。
- 同一 Session、同一目录的写操作、不可重复的外部副作用，需要排队或隔离。

这也是 PX 的一项基础能力：管理队列、取消、超时、资源上限和恢复，而不是把“并发”简单理解为同时启动更多模型请求。


7. 先做一条完整链路

PX 不应该从完整生态开始。第一版最重要的不是支持多少 Connector，而是证明下面这条链路真的有用：

1. 应用通过兼容接口创建一个任务；
2. PX 启动或恢复一个 Pi Session；
3. Session 完成一段工作并留下 Watch；
4. 外部事件到达后，PX 去重并重新唤醒它；
5. 应用可以继续看到同一个 Session 的结果。

如果这条链路成立，Serve、Watch、持久化和恢复才不再是孤立的工程模块，而会变成一种新的使用方式：把 Agent 当成一项可以持续推进的工作，而不是一次性聊天请求。


一句话描述 PX

PX 不是另一个 Agent runtime。它是 Pi 的服务层、生命周期层，以及让停止的工作在未来继续发生的那一小段基础设施。
